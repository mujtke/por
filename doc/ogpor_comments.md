## OGTRansfer

假设此时尝试将图`G`从状态`s0`迁移至状态`s1`

### SimpleStepTransfer

根据当前所处的临界区状态`caa`（由状态`s1`中包含的`OGPORState`确定），分成四种情况进行处理：

```c
__VERIFIER_atomic_begin();  // S1
X = X + 1;									// S2
__VERIFIER_atomic_end();		// S3

Y = Y + 1;									// S4

a = a + 1;									// S5
// X, Y 为全局变量，a为局部变量
```

* `handleBlockStart`，对应了语句`S1`
* `handleBlockContinue`，对应了语句`S2`
* `handleBlockEnd`，对应了语句`S3`
* `handleBlockNotIn`，对应了语句`S4`和`S5`

除了语句所处的临界区状态之外，语句本身被分为四种类型：

* 0：仅访问局部变量的非假设语句
* 1：仅访问局部变量的假设语句
* 2：访问全局变量的非假设语句
* 3：访问全局变量的假设语句

除临界区状态之外，利用状态`s0`和状态`s1`还可确定当前迁移边所处的线程`curThd`。因为图`G`中维护着每个线程当前对应的观测图节点，因此可知当前线程对应的节点`node`。

#### 冲突类型的定义和检测

图传递过程中的冲突定义为：图`G`中存在来自于其他线程的未被探索的节点，这些节点需要先于当前节点`node`发生。

若检测时通过图`G`中存在的边直接推导出冲突，则为基本冲突。在图中存在的边的基础上，需结合进一步推导才能得出的冲突，为`mo`冲突（目前仅考虑通过`mo`关系进行进一步推导。

##### 检测基本冲突

通过检查当前节点`node`和来自其他线程的未被探索节点之间的`po`，`rf`和`fr`关系来确定是否冲突。若存在来自其他线程的未被探索的节点需要先于当前节点`node`发生，则冲突存在。

当冲突存在时，记基本冲突检测的结果为`TRUE`，无冲突存在则记为`NONE`。

存在环路时，无法确定当前节点`node`和来自其他线程未被探索节点之间的先后顺序，因此采用如下规则：

* 若当前节点`node`中包含可以被回访的事件，则记检测结果为`TEMP`。（**用是否包含可回访事件这个条件，可行吗？**）
* 否则，记检测结果为`TRUE`，记视作存在冲突。

##### 检测mo冲突

此类型的冲突检测主要是检测节点`node`中的写事件，是否引起了一些探索顺序上的矛盾。因此，检测需要等待节点被完全探索之后才能进行（此时节点中的写事件的`mo`更新完成）。

以节点中的写事件`ce`为例，分别对其`mo`祖先和后代进行检测：

* 若`mpe`为`ce`的`mo`祖先，则当存在读事件`r`从`mpe`处读值，但`r.inNode`仍然处于未被探索状态时，检测到`mo`冲突。因为`r.inNode`需要先于当前节点`node`被探索。

* 若`msuc`为`ce`的`mo`后代，且存在从`ce`处读值的读事件`r'`满足下列条件：

  * `msuc`先于`r'`发生
  * `msuc.inNode`处于未被探索状态
  * `r'.inNode`处于未被探索状态

  则认为发生了`mo`冲突，因为此时若是先探索当前节点`node`，则后续的探索中`r'`应该从`msuc`处读值，这与`r'`从`ce`处读值矛盾。



### handleBlockStart

假设语句不会开启一个原子块，此情况下只处理语句类型为0和2的两种情况。

#### edgeType = 0 (start)

* 若`node`不为空，表明当前我们准备进入`node`。此时需要进行冲突检测，即检测是否有来自其他线程的节点应该被优先探索。

  此过程中，冲突检测的过程如下：

  * 首先[检测基本的冲突类型](#检测基本冲突)`ConflictType`
  * 根据基本冲突类型，分类处理
    * `TRUE`：结论为冲突存在，存在来自其他线程的节点需要被优先探索
    * `NONE`：[检测mo冲突](#检测mo冲突)，若存在mo冲突，则根据`node`是否包含需要回访的事件确定结论。若`node`中存在需要回访的事件，则即便存在mo冲突也先对`node`进行访问。（mo冲突不是硬限制，可能在回访之后消失？）
    * `TEMP`：同`NONE`。

* 若`node`为空，表明我们准备开启一个新的节点。此时需检测是否图`G`中还存在尚未被探索的节点，仅当不存在这样的节点时，我们才能开启一个新的节点。开启新节点之后，需要对该节点进行访问（`graph.visitNode`）来更新节点的关系

  一般情况下，开启一个原子块的语句是某个函数调用语句，因此此时更新节点关系往往只是设置节点的`to`和`po`。

#### edgeType = 2 (start)

处理方式与[edgeType = 0](#edgeType = 0 (start))相同。



### handleBlockContinue

此情况下会遇到0，1，2，3四种语句类型。

当位于一个复杂原子块内部时，不进行冲突检测。

#### edgeType = 0 (continue)

根据节点是否已经被添加到图`G`中，以及节点是否已经包含相应的边，确定是否进行添加边的操作。因为该边仅仅访问局部变量，因此不会给节点增加新的事件。

#### edgeType = 1 (continue)

* 若节点已经添加到图中，且节点包含该边， 则不针对该边进行多余的操作。
* 若节点已经添加到图中，但节点不包含该边时，需要进行特殊处理：`handleAssumeEdgeNotInNode`，即[处理假设语句不在节点内的情况](#handleAssumeEdgeNotInNode)。
* 若该节点是一个全新的节点（即尚未添加到图中），也需要进行特殊处理：`handleAssumeEdgeWithNewNode`，即[处理向全新节点添加假设语句的情况](#handleAssumeEdgeWithNewNode)。

#### edgeType = 2 (continue)

处理方式同[edgeType = 0 (continue)](#edgeType = 0 (continue))，区别在于由于此时的边访问了全局变量，因此需要给节点添加新的事件。

#### edgeType = 3 (continue)

处理方式同[edgeType = 1 (continue)](#edgeType = 1 (continue))。



#### handleAssumeEdgeNotInNode

输入条件：当前图为`G`，当前节点为`node`，当前迁移边为`edge`。`edge`不在`node`中，同时`node`并非一个全新添加的节点。

假设`edge`=`a < 1`，则其`coCFAEdge`=`!(a < 1)`，其`coARGEdge`=`!(a < 1)`。`coCFAEdge`和`coARGEdge`的区别在于，前者一定存在（根据CFA得到），而后者不一定存在（根据ARG得到）。

根据`coCFAEdge`是否位于节点中以及`coARGEdge`是否存在，分成下列四种情况进行处理：

* `coCFAEdge`位于节点中，`coARGEdge`不存在 （case 1）

  * 若`edge`仅访问局部变量，则通过将`node`中的`coCFAEdge`替换成`edge`，实现节点和实际ARG路径的一致。
  * 若`edge`访问全局变量，则无法进行替换，因为图`G`能够通过read from关系记住全局变量及其所在边。因此此时发生了假设语句冲突，因为图`G`记住的边（即`coCAFEdge`）与实际路径中遇到的`edge`不一致，且`coARGEdge`不存在（若存在则图`G`可沿着该边传递）。此时的情况视作异常。

* `coCFAEdge`不位于节点中，`coARGEdge`不存在 （case 2）

  此情况被认为是最近一次的回访导致`edge`从`node`中被移除。因此将`edge`添加到节点中即可（包括可能的事件）。

* `coCFAEdge`不位于节点中，`coARGEdge`存在（case 3）

  此情况下，`edge`和`coCFAEdge`均不位于图`G`中，而`edge`与`coARGEdge`均存在，表明实际的路径中遇到了不确定性赋值。

  * 若此时是图`G`第一次遇到`edge`，则此时需要额外产生一张新的图`coG`，且将`edge`记录下来。

  * 若`edge`已经被图`G`所记录，则不用产生新的图，将图`G`沿着`edge`进行传递即可。

* `coCFAEdge`位于节点中，`coARGEdge`存在 （case 4）

  此情况下图`G`应该沿着`coCFAEdge`传递，即`G`不能沿着`edge`进行传递。

  

#### handleAssumeEdgeWithNewNode

输入条件：当前图`G`，当前节点`node`，当前迁移边`edge`。`node`是全新添加的节点，因此`node`一定不包含`edge`

此情况下，

* 若`coARGEdge`不为空，则表明存在不确定性赋值，需要产生新图`coG`。同时若`edge`不访问全局变量，则`G`还需将其记录。需注意的是，`coG`此时不需要记录`coARGEdge`，后续在尝试传递`coG`时再记录即可。

* 若`coARGEdge`为空，则表明不存在不确定赋值，不用产生新的图`coG`，让图`G`沿着`edge`传递即可，同时添加`edge`和相应的事件。



### handleBlockTerminated

#### edgeType = 0 and edgeType = 2

`edgeType=0`和`edgeType=2`的两种情况处理方式同[handleBlockContinue](#handleBlockContinue)。

#### special case

需要注意的是，某些类型的边会导致程序提前终止（例如`abort()`函数调用），从而造成原子区域的不闭合。我们将此类情况也视作原子区域结束。由于发生`abort()`函数调用时，程序直接终止，因此对于当前原子区域而言，其在ARG中的最后一条边并非`abort()`，而是位于`abort()`之前的一条边。对于该边而言，`edgeType=1`或`edgeType=3`。对于该边的处理同[handleBlockContinue](#handleBlockContinue)。

### conflict detecting

虽然对于边的处理方式与[handleBlockContinue](#handleBlockContinue)相同，但此情况下（即原子区域结束）需要进行冲突检测。检测过程与[handleBlockStart](handleBlockStart)类似。



### handleBlockNotIn

#### edgeType = 0 (not in)

说明没有遇到节点，也不用开启新节点。

#### edgeType = 1 (not in)

此情况同样不用处理节点。若不存在不确定性赋值，则可以将图直接进行传递，否则，需要判断图`G`是否可以沿着该边传递。

在不确定性赋值存在的情况下，若该图是第一次沿着该路径进行传递（变量`isSimpleTransfer`为真）， 则需要对图进行复制，并保留副本。若并非第一进行传递，则需要对比当前边和图中存储的边是否一致，在一致的情况下才能将图进行传递。

#### edgeType = 2 (not in)

由于此时边中包含共享变量，因此需要根据当前节点`node`是否为空来分别进行处理：

* 若`node `不为空，则此时我们准备进入该节点，需进行冲突检测。
* 若`node`为空，则此时准备创建新的节点。若图`G`中不存在未被探索的节点，则可创建新节点，否则需要优先探索图中未被探索的节点。

#### edgeType = 3 (not in)

此时同样需要根据当前节点`node`是否为空分别进行处理：

* 若`node`不为空，则此时我们准备进入该节点，需要进行冲突检测。需要注意的是，此时节点应该包含当前边，否则视作发生了假设语句冲突的错误。
* 若`node`为空，此时若图`G`中不存在未被探索的节点则可创建新节点。由于此时的边为假设语句，若存在不确定性赋值，还需对图`G`进行复制。



## OGRevisitor

给定图`G`，对其进行回访的过程如下：

* 获取图`G`中待回访的事件集合`RE`。
* 依次序对`RE`中的事件进行回访。

#### 获取回访事件的集合

获取图`G`中的可回访事件时，需要用到最后被添加到图中的节点`lastNode`。对于该节点而言，我们维护了两个指针`LHRIndex`和`LHWIndex`，分别记录了对于该节点而言，最后回访的读事件和写事件的索引。

分别取出索引大于`LHRIndex`的读事件和索引大于`LHWIndex`的写事件，并且让所有的读事件排在写事件之前，即得到所有待回访的事件。

#### 获取回访时的候选事件

给定一个读事件`r`，对其进行回访时，按照下述规则挑选候选的事件：

* 暂时忽略`r`所在节点中位于`r`之后的读事件的`rf`关系，同时也暂时忽略`r`的`rf`关系。

* 遍历图中的节点，忽略以下节点：

  * 位于图中，但是尚未被探索的节点

  * `r.inNode`

  * `r.rf.inNode`

  * 不包含与`r`访问相同变量的写事件的节点

  * 是`porfPres`中某个节点的因果前驱的节点

    `porfPres`：不满足之前四个条件，且是`r.inNode`的因果前驱的节点。

* 对于遍历过程中未被忽略的节点`nodei`，其中与`r`访问相同变量的写事件可以作为候选事件。若该节点是`porfPres`中某个节点的因果前驱，则将该节点添加到`porfPres`中，然后继续遍历剩余节点。

* 按照添加顺序从后往前遍历所有节点。



给定一个写事件`w`，对其进行回访时，按照下述规则挑选候选的事件：

* 按照添加顺序，从`w.inNode`的前一个节点开始从后往前遍历所有节点。

* 忽略以下的节点：

  * 不包含与`w`访问相同变量的读事件的节点

  * 节点中与`w`访问相同变量的读事件`r`是`w`的因果前驱

  * 节点中包含于`w`访问相同变量的读事件`r`，但该节点还满足下述条件：

    * `r.rf.inNode`处于未探索状态
    * 在忽略`r`及其之后的读事件后，`r.rf.inNode`仍然是`r.inNode`的因果前驱。

    此情况下，令`r`从`w`处读值会推导出`r`是`r.rf.inNode`这样的矛盾。

* 对于遍历过程中未被忽略的节点`nodei`，其中与`w`访问相同变量的读事件可以作为候选事件。



### 对读事件的回访

给定读事件`r`和候选事件`w`，对`r`进行回访需要考虑以下几个步骤：

* 由于回访令`r`从一个新的写事件处读值，因此需要将节点中在`r`之后添加的事件暂时移除。

* 在移除了需要移除的事件之后，令`r`从`w`处读值，由于`w`可能包含不确定性赋值，因此需要分情况处理：

  * 若`w`不包含不确定性赋值，则令`r`从`w`处读值时，若`r`所在边为假设语句，则可以根据读值结果确定是否需要将`r`所在的假设语句进行变更（例如从`x < 1`变更为`!(x < 1)`）。

  * 若`w`中包含不确定性赋值，则令`r`从`w`处读值时，若`r`所在边为假设语，则需要考虑`r`所在的假设语句变更和不变更两种情况，即此情况下，令`r`从`w`处读值会得到两个图作为结果。

    假设`r`所处语句为`x < 1`，则当`w`为不确定性赋值时，令`r`从`w`处读值会得到这样的两个图：一个图保持`r`所在边为`x < 1`，而另一个则是将`r`所在边变更为`!(x < 1)`。

* 在令`r`从`w`处读值后，对得到的图（可能不止一个）进行一些后处理。



### 对写事件的回访

给定写事件`w`和候选时间`r`，对`w`进行回访需要考虑的步骤包括：

* 令`r`从`w`处读值，会导致在`r`之后添加的事件被移除（需要排除`w`的因果前驱事件），即被删除事件的集合为`delete`
* 令`deletePlusR = delete + { r }`，为保证不会遗忘先前回访的结果，只有当`deletePlusR`中所有的事件均是最大化添加时，针对`w`的回访才能继续进行。
* 若`deletePlusR`中的所有事件均被最大化添加，则回访可以继续进行。移除`delete`中的所有事件，然后令`r`从`w`处读值。类似的，需要处理不确定性赋值的情况。
* 对得到的图进行后处理。

#### 获取delete

给定读事件`r`，令其从一个新的写事件`w`处读值时，在该事件后添加的事件需要被移除：

* 若`r`为待回访事件，则只需移除`r`所在节点中位于`r`之后的事件。
* 若`w`为待回访事件，则除了移除`r`所在节点中位于`r`之后的事件外，还需移除部分在`r.inNode`之后添加的节点。对于在`r.inNode`之后添加的节点`n`，若其是`w`的因果前驱，则该节点需保留，否则需要进行移除。

#### 最大性检查

最大化检查仅需在对写事件`w`进行回访时进行，假设此时准备令`r`从`w`处读值。

对于`delete`中的某个事件`e`，按照如下方式检测`e`是否为最大化添加：

* 首先获取关于事件`e`的`previous`。`previous`包含了图中所有在`e`之前添加的事件（包括`e`），以及事件`w`的所有因果前驱。
* 若`e`为写事件，则令`ep = e`，否则令`ep = e.rf`。若`previous`不包含`ep`，则说明`e`并非最大化添加。（此时说明`e`为读事件，且从一个在`e`之后添加的写事件处读值）。
* 取`previous`中的事件逐一进行判断，假设取出的事件为`ee`：
  * 若`ee`为读事件，`e`为写事件，且`ee.rf = e`，则说明`e`并非最大化添加。
  * 检测是否存在事件`empo`，该事件是`e`的`mo`后代并且和`w`不在相同节点中，同时该事件存在于`previous`中，则说明`e`并非最大化添加。



#### 对回访得到的图进行后处理

假设回访得到的图为`G`

* 若`G`满足一致性，则将`<G.pivotState, G>`添加至回访结果中。
* 若`G`不满足一致性，则：
  * 若`G`中还存在需要回访的事件，则继续对`G`进行回访
  * 若`G`中不存在需要进行回访的事件，则先将`<G.pivotState, G>`添加到回访结果中，等候后续可能的回访（因为此时`G`可能因为移除了某些事件而变得不能回访，而在后续探索过程中，随着节点的补全，`G`可能重新变得可回访）。

获取`G.pivotState`：目前采用简单的处理方式，默认使用`G`中添加的第一个节点的前驱状态（保存在节点中）作为`pivotState`。

q获取到`pivotState`之后，将图`G`放到`pivotState`处，同时清空`G`中的`to`关系，并将所有节点标记为未探索。

在后续传递`G`的过程中（需要将`G`传递至某个处于等待探索状态的状态处），`G`中的`po`和`rf`关系保持不变，`mo`和`fr`关系随着图的传递动态更新。
